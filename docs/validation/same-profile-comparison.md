# Same-profile runtime comparison — 2026-10-28

The controlled run reused Tropa's existing test registration, pinned WarpScout 0.16.1 and pinned mihomo 1.19.33. Official WARP was checked as disconnected. The router was left in the user's last reported state (zapret enabled). Only loopback proxy listeners were started; no host TUN, route, DNS or proxy settings were changed.

WarpScout scanned 70 sampled IPv4 addresses with AWG and `-P`, reporting 66 working candidates in 25.56 seconds. The diagnostic retained those exact endpoints and the exported AWG parameters. It tested a reconstruction of Tropa's current proxy configuration with HTTPS WARP trace, five UDP DNS queries and the scanner's HTTPS meta target. Failed attempts were followed by a control using the original exported proxy at the same endpoint and with the same account.

The bounded validation run checked 39 of the 66 candidates: 29 passed and 10 failed. The remaining 27 were not tested before the 450-second diagnostic budget was reached; finishing the current candidate/control brought cumulative probe time to 484.4 seconds. Eight of the ten original-export controls passed and two failed. A failed attempt commonly took about 40 seconds, while a passing attempt usually took less than a second. One reconstructed-profile attempt passed the initial HTTPS trace but then failed all five DNS queries and the later HTTPS meta request.

These results demonstrate that a smaller validated list can include both failed attempts and candidates not reached within the budget. They do not prove that every rejected candidate is permanently unusable, or that every address in a successful scan remains usable later.

A second experiment reused the first failed endpoint and changed only one setting at a time: local IPv6 address, MTU, or explicit peer syntax. It also repeated the unchanged baseline and original export, reversing the order in the second round. The unchanged Tropa configuration passed both repetitions; the original export failed once and passed immediately on its unchanged repetition. The other variants passed both repetitions. This small experiment does not establish a configuration-specific cause, so no networking configuration change is justified by it. Possible network/path/runtime causes remain unresolved.

Evidence is in `.artifacts/native-connection/same-profile-2026-10-28/` and `.artifacts/native-connection/isolate-profile-2026-10-28/`. These are throwaway Python diagnostics using curl for HTTPS, not a replay through Rust's reqwest client or a test of the packaged native UI. They cannot establish the exact cause of the earlier 46-profile result. Temporary account exports and runtime configurations were removed in both runs; owned child processes exited. The existing test registration was preserved.

The resulting product correction preserves the latest extended-search counters after completion, failure or cancellation. The server panel separates untested candidates from failed checks and explicitly reports reaching the search time limit. Cancelled and infrastructure-failed checks do not count as rejected endpoints; successful checks count as verified only after catalog persistence. Network acceptance criteria, search budgets and manual selection semantics are unchanged.

391 backend tests and 48 frontend tests passed. Regression tests first reproduced lost summary state and incorrect cancellation counts, then passed after correction. TypeScript, changed-file ESLint, focused Rust formatting, frontend build and `git diff --check` passed. Independent read-only review caught the cancellation misclassification and found no important issues after correction. Native click-driven rendering and accepted-UAC startup of the new package remain unverified.
