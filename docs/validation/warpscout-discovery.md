# Интеграция WarpScout — 27 октября 2026

## Что реализовано

Developer probe теперь принимает третий необязательный аргумент — абсолютный путь к закреплённому `warpscout.exe`. Он запускает поиск, строго разбирает единственный результат `IP:порт`, передаёт его в существующую проверку mihomo и сохраняет `warp-endpoint.json` только после успешных HTTPS WARP trace и DNS UDP. Обычный запуск probe читает этот сохранённый адрес; повреждённый файл даёт ошибку.

WarpScout вызывается с `scan -proto wg -best -plain -no-report -sample 5 -tunnel-jobs 12 -timeout 2 -account <temporary-secret>`. Лимит — 180 секунд. Сканер использует собственный userspace-туннель; рабочее подключение дополнительно проверяется тем же mihomo, который выбран для Tropa. На этом этапе только один лучший кандидат от каждого запуска, без списка серверов и без автоматического перехода на другие протоколы.

Отмена Ctrl+C общая для сканирования и последующей проверки; сигнал сохраняется между фазами. Windows Job Object, shared execution reservation и явный kill/wait ограничивают владение дочерними процессами. Файл для сканера содержит только ключи и адреса туннеля, без Cloudflare API token/id, и удаляется после остановки. Вывод ограничен, строки stderr сканера не публикуются.

## Реальные проверки

Первый прогон (4 работника, 120 секунд) закончился именно таймаутом. Регистрация осталась неизменной; временный account-файл удалён; процессов scanner/core не осталось; снимки адаптеров, default routes и ProxyEnable совпали. Рабочий endpoint не сохранён. Это незавершённый поиск, а не доказательство отсутствия доступных endpoint.

По исходникам: первая фаза проверяет 12 адресов; при отсутствии основных портов последовательно проверяет ещё 50 портов на каждом адресе. Поэтому исходный бюджет уточнён до 12 работников и 180 секунд. Это изменение параллельности и времени, не способ обхода ограничений.

## Проверка оригинального WarpScout без адаптера Tropa

По дополнительному запросу пользователя официальный exe запущен напрямую. Его хэш после тестов совпал с исходным; исходники и бинарник не менялись.

1. `scan -proto wg -plain -no-report -account <temporary-account>` с существующей регистрацией: первая фаза получила handshake на портах 2408, 500, 1701, 4500; вторая проверила 70 адресов и завершилась `no working endpoints found - try -p awg -gen-i1 quic`, exit 1.
2. Для независимости от регистрации Tropa выполнена штатная команда `register -plain -relay none -account <native-account>`: exit 0. Использован прямой Cloudflare API без стороннего relay. Оригинальный WarpScout также штатно сохранил дополнительные MASQUE/outer регистрации; эти реквизиты не импортировались в Tropa.
3. С собственной новой регистрацией повторён тот же штатный WG scan. Снова handshake на четырёх основных портах, затем 70 проверок и тот же `no working endpoints found`, exit 1.

Итог: отказ второй фазы воспроизводится вне Tropa. По исходникам эта фаза требует запроса metadata через туннель (включая DNS); положительный handshake ещё не означает успешную передачу данных. Конкретная причина отказа не установлена. AWG, MASQUE и подсказка `-gen-i1 quic` не запускались автоматически.

Состояние адаптеров, default routes и ProxyEnable после тестов совпало с исходным, оставшихся scanner/core процессов — 0. Временная копия реквизитов Tropa удалена, отдельная нативная регистрация сохранена в исключённой `.artifacts/warpscout-stock-test/secrets/native-account.json` для повторных самостоятельных тестов.

Доказательства: `.artifacts/warpscout-stock-test/stock-scan.log`, `stock-native-scan.log`, `stock-register-result.json`, `cleanup.json`. Логи поиска не содержат ключей.

Полный набор Rust app-library: 370 passed, 0 failed. Developer probe собран; форматирование новых файлов проверено. Read-only review выявил и помог устранить потерю отмены между фазами. Безопасная классификация stderr дополнительно проверена тестом; после её добавления живые тесты выполнялись напрямую оригинальным WarpScout, без адаптера.

## Сравнение с установленным официальным WARP

По просьбе пользователя прочитано состояние уже подключённого Cloudflare WARP без отключения или смены настроек. `warp-cli 2026.1.150.0`: Connected, Network healthy; `tunnel stats`: **MASQUE (HTTP/2)**. Endpoint — **162.159.198.2**, активное TCP-соединение службы подтверждает порт **443**. Предпочтение клиента: MASQUE HTTP/3 с fallback на HTTP/2; фактически выбран HTTP/2.

Независимые HTTPS-запросы Cloudflare trace по IPv4 и IPv6 вернули `warp=on`, colo `HEL`. Публичные адреса пользователя в этот документ не записываются. Регистрация и ключи установленного клиента не извлекались.

Это подтверждает работоспособность официального клиента по другому транспорту, чем проверенный WarpScout WireGuard. Причина отказа WG ещё не установлена. Следующее обоснованное направление — отдельная проверка MASQUE HTTP/2 и совместимости с выбранным ядром. Испытание стороннего туннеля при активном официальном WARP дало бы вложенный маршрут; оно не заменяет проверку прямой доступности через роутер.

## Границы интеграции

Это backend/developer-интеграция. Кнопка поиска, прогресс и отмена в GUI ещё не подключены. Игровой TUN, главный переключатель, выбор страны и готовый portable ZIP не подтверждены этим тестом. До запуска GUI остаётся изоляция upstream updater. Доступность адреса или положительный результат WarpScout без прохождения mihomo не обозначается как готовое подключение Tropa.
