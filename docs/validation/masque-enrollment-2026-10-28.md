# MASQUE enrollment implementation — 2026-10-28

This starts milestone 5 of the approved roadmap. No Cloudflare registration request, downloaded executable, Tropa, UAC or tunnel was run. Completed native enrollment/runtime remains unproven.

## Source contract

Pinned WarpScout v0.16.1 `masque.go` uses `https://api.devices.cloudflare.com/v0a4471/reg`, User-Agent `WARP for Android` and CF-Client-Version `a-6.35-4471`. POST creates an initial device using a random 32-byte placeholder with key_type `curve25519` and tunnel_type `wireguard`, serial_number, install_id/fcm_token, current UTC ToS timestamp, model/OS/locale. This is a separate device registration, not conversion of Tropa's existing WG registration. The returned ID and token authenticate PATCH /reg/{id}; PATCH enrolls the base64 P-256 public SPKI DER with key_type `secp256r1`, tunnel_type `masque` and a device name.

WarpScout generates the local EC key with Go ecdsa/P256, exports the private key using x509.MarshalECPrivateKey (SEC1/RFC 5915 DER) and its public key using x509.MarshalPKIXPublicKey (SPKI). The enrolled server peer is PEM PUBLIC KEY; interface v4/v6 addresses come from the enrolled response. Pinned mihomo v1.19.33 `adapter/outbound/masque.go` specifically calls x509.ParseECPrivateKey and x509.ParsePKIXPublicKey on its base64 private-key/public-key fields. PKCS#8 private data or a WG X25519 secret cannot be substituted. H3 and H2 share the same EC identity.

References were read as source only: `.artifacts/research/upstream-review-2026-10-28/vernette__warpscout/source/masque.go`, `Diniboy1123__usque/source/cmd/register.go` and `MetaCubeX__mihomo/pinned-v1.19.33/adapter/outbound/masque.go` under the same research root.

## Implemented foundation

`config/warp_masque_account.rs` generates fresh P-256 keys with aws-lc-rs, exports private SEC1 DER and public SPKI DER, and checks that decoded private/public values form one canonical pair. It rejects WG-sized raw private keys and mismatched public keys without including input bytes in errors. The secret-bearing types deliberately have no Debug implementation.

The separate `secrets/masque-pending.json` stores a versioned MASQUE pending device ID, token and EC pair. Reads/writes are bounded to 64 KiB, unknown fields and invalid versions are rejected, and IDs/tokens/keys are validated before saving. Writes use the existing atomic file helper. Loading invalid data does not erase it or silently generate another identity. WG account/pending files are not read or modified by this store. The existing portable plaintext-secret storage decision is preserved.

Direct dependency aws-lc-rs is pinned to 1.18.1 with default features disabled and non-fips/alloc enabled. This exact version was already used by rustls and cached locally. Its declared license is `ISC AND (Apache-2.0 OR ISC)`. Default ring compatibility features initially requested an uncached `untrusted 0.7.1`; offline resolution rejected that attempt before compilation or download. Using only the required existing features avoided the extra package. Comparison against the pre-change lockfile confirms no package versions were added, removed or upgraded: only clash-verge's direct dependency record gained aws-lc-rs. No cryptographic algorithm or DER serializer was implemented manually.

## Increment 2: completed identity and local HTTP enrollment

`MasqueAccount` now accepts the enrollment response only after validating the original confirmed POST identity, the server's PEM PUBLIC KEY as a canonical P-256 SPKI DER key, and assigned IPv4/optional IPv6 addresses. Loopback, unspecified, multicast and link-local addresses are rejected; an empty/missing v6 is allowed. It stores the peer key as base64 SPKI for the future mihomo builder, separately from the device's own enrollment public key. Replacement ID/token fields in PATCH responses do not replace the authenticated POST identity. Secret-bearing objects still have no Debug implementation.

The versioned, bounded `secrets/masque-account.json` uses the existing atomic writer. Reads validate the complete stored identity and do not erase or regenerate invalid files. `clear_pending` is separate; persistence of the completed identity precedes cleanup. A completed account remains authoritative when an earlier pending record could not be removed.

`core/warp_masque_registration.rs` now implements the pinned POST/PATCH contract through a direct reqwest client: explicit version/User-Agent headers, local P-256 generation before POST, random 32-byte initial placeholder and 8-byte serial, millisecond UTC ToS timestamp, public-SPKI-only PATCH, and a Tropa device name. Automatic HTTP retries and redirects are disabled, request duration is bounded (5-second connect/15-second total), and response streaming is capped at 64 KiB. Request/response bodies, URLs and tokens do not appear in returned errors. Local confirmed POST data is persisted before PATCH. `ensure_registration` first reuses completed state, then resumes pending enrollment, and only creates a device when both are absent. It must be called under the coordinator's registration/config ownership when wired into production; it is not yet exposed as a GUI command or background operation.

An enrollment 401/404/410 returns a typed unusable-registration error and preserves pending state for explicit reset. A 403 remains a generic API rejection: access denial alone does not prove that a token has been revoked. No silent replacement POST is performed in that failure path. An ambiguous initial POST can still leave an unknown remote device if its response never arrives; no claim is made to recover a server ID that was never received. Explicit family reset/status and catalog fingerprints remain follow-up work.

Local test evidence:

- The completed-account regression first failed on the missing model/store API, then passed. It rejects incomplete responses, invalid peer PEM and invalid addresses without losing pending; it checks completed restart persistence, peer/identity distinction and optional IPv6.
- The HTTP workflow regression first failed on the absent client/workflow, then passed. The loopback server accepts POST and drops the first PATCH response. A subsequent client resumes PATCH only with the same identity/public key. A completed restart succeeds after the test server has stopped, proving no HTTP request is required for that local reuse. Captured requests check public-only material, protocol/version headers and bearer authentication; WG marker bytes remain unchanged.
- A targeted failure reproduced misclassification of HTTP 403 as revoked; after correction the matrix passes for revoked statuses, access denial, throttling, malformed JSON, missing enrollment fields and oversized body. Failed enrollments preserve pending bytes and never commit a completed account. Synthetic response/token contents are absent from returned errors.
- A real local request timeout produces typed `Timeout` and retains the original pending bytes. The stalled loopback task is explicitly released and awaited.
- A loopback response hook creates a directory at the completed-file path after the initial account read. Enrollment succeeds but atomic commit fails; pending remains. Removing only that test obstruction and retrying resumes PATCH and commits successfully. This covers the workflow commit barrier, not just an isolated file writer.

Final verification for this increment: `cargo test --locked -p clash-verge --lib --features clippy,portable,tropa-probe --offline --quiet` passed all **422 tests**, exit 0, without compiler warnings. Scoped Rust files were formatted. Failed-test temporary data was inspected and removed by exact path; successful tests remove their own files, and no `tropa-masque-*` test directories remained. Frontend checks were not repeated because no frontend or wire contract changed. No Cloudflare request, Tropa GUI, TUN, UAC prompt, downloaded program, service or network-settings change occurred.

This does not complete milestone 5: safe status/reset commands, family-specific catalog binding, coordinator integration and the deferred native registration/mihomo-format acceptance gate remain. MASQUE H3/H2 production transport is still not integrated.


## Increment 3: family status/reset, settings and catalog binding

Added the safe MASQUE status contract (`missing`, `pending`, `registered` with `hasIpv6`). No device ID, token, address or key is included. A committed account takes precedence over leftover pending data. The read-only Tauri status command serializes through the configuration owner. The reset command also takes the connection idle guard, checks that Core is not running, and takes the catalog lock; it cannot reset an active or incompletely cleaned connection.

Explicit MASQUE reset creates a replacement while retaining the previous completed account until enrollment and atomic commit succeed. A failed reset leaves that account intact and a subsequent reset resumes a different pending identity instead of issuing another POST. A leftover pending record matching the committed device is discarded before starting an explicit reset. A known unusable pending token can be replaced once during explicit reset; automatic ensure still preserves that pending identity and returns the error. Invalid pending state can be removed only in this explicit reset path. WG files are not touched. The new local HTTP regressions first failed on the absent reset/status API, then passed, checking old completed bytes, the same resumed public/private pair and WG marker bytes.

`WarpCatalog` now binds WG/AWG and MASQUE H3/H2 independently. The legacy `registration_fingerprint` remains the hash of the WG device ID, so existing version-1 WG catalogs retain their manual choice and evidence when that identity is unchanged. An optional `masque_registration_fingerprint` hashes the MASQUE device ID and device enrollment public key (not the server peer); raw ID/token/key values are not written to the catalog. H3 and H2 share this binding. A changed or unavailable identity invalidates only its own family's validation and rejection evidence. Previously validated profiles become untested rows, with their reproducible endpoint/parameters and existing manual pin retained; they do not silently become Automatic. Old scanner observations remain dated scanner evidence, not new runtime validation. Demotion still observes the existing scanner catalog bound and preserves the pinned row during eviction.

An unavailable/corrupt identity is treated as unavailable for that family's catalog evidence, while its status command reports the read error. This lets a broken MASQUE file leave valid WG/AWG rows usable; neither identity file is silently deleted or rewritten. Tests cover both invalidation directions, changed MASQUE keys with the same device ID, retained manual validation target, legacy WG file loading, corrupt MASQUE data, persistence and non-disclosure. The family-binding regression first failed on the missing MASQUE binding API; the existing WG identity-change expectation was deliberately updated from silent Automatic fallback to preservation of the manual target.

The registration screen now displays separate WG/AWG and MASQUE status/error/reset sections. Reset confirmation identifies the family and explains the independent registration. Both buttons are disabled while connected, during an operation or when shutdown remains incomplete. Mutations use the existing intent funnel, and queries are refreshed after connection work and reset. Frontend tests verify independent pending/read-error display and both disabled reset buttons. Their first run failed because the new component was absent, then passed. The Tauri command boundaries return safe statuses, not the persisted secret-bearing objects.

Verification: all **426 Rust library tests** passed with the locked/offline portable/probe/clippy test configuration, without compiler warnings; the strengthened reverse-family assertion passed again in a targeted rerun. All **57 frontend tests in 15 files**, TypeScript checking, scoped ESLint and Vite production build passed. Test-owned temporary files were removed. No Tropa process, UAC prompt, native tunnel, Cloudflare registration request or downloaded program was started, and no service/network setting was changed.

Remaining work: automatic MASQUE registration is not yet called by the connection/discovery coordinator because those paths still reject MASQUE runtime profiles. The family binding foundation and settings are present, but end-to-end family binding during actual MASQUE validation must still be checked when runtime integration lands. Native enrollment and mihomo acceptance remain deferred. Milestone 5 therefore remains open; milestone 6 (H3/H2 runtime) is next.
