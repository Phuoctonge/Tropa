## Архитектура по фактическому коду

```text
Electron main + React UI
    ├── WarpPlusManager → warp-plus либо masque-plus → локальный SOCKS
    ├── SingBoxManager → gRPC → повышенный oblivion-helper → TUN sing-box
    │                                                      └── SOCKS outbound
    ├── usque register → MASQUE config.json
    ├── NetStatsManager → отдельный zag-netStats
    └── SpeedTestManager → @cloudflare/speedtest
```

Desktop формирует CLI и обрабатывает события; криптографический обмен, реализация транспорта и алгоритмы встроенного сканера находятся в других компонентах. `script/dlBins.ts:76` указывает источники WarpPlus, Oblivion Helper, MasquePlus и вспомогательных EXE; `src/main/config.ts` фиксирует WarpPlus 1.2.6, Helper 1.3.2, NetStats 1.0.2, ProxyReset 1.2.14, MasquePlus 2.9.0. Исходный код этих отдельных engines в загруженном desktop-дереве не содержится. Нельзя на основании одной этой оболочки утверждать, что изучены все детали их регистрации, UDP, обхода ограничений или привилегированного сервера.

## Существенные отличия от требований Tropa

### 1. Правила приложений исключают их из туннеля

`RoutingRuleParser.processAppRule` в `src/main/lib/sbHelper.ts:106` добавляет имена EXE. `sbConfig.ts:387` отправляет `processSet` в `outbound: direct`, а финальный маршрут `sbConfig.ts:500` остаётся `proxy`.

Таким образом, `app:firefox.exe` означает «Firefox напрямую, остальное через proxy». Это обратная политика относительно согласованного режима Tropa «только выбранные приложения через WARP». Сравнение идёт по имени, а не по полному пути; разные установки с одинаковым именем не разделены. Портировать этот парсер как готовый split tunneling нельзя.

### 2. Portable ZIP не означает все данные рядом с EXE

`src/constants.ts:40` задаёт `workingDirPath = app.getPath('userData')`. В него копируются engines, там находятся configs, cache и служебные файлы; logs/temp также используют системные каталоги. В полном дереве не найдены переопределение `userData` через `app.setPath` и обработка `PORTABLE_EXECUTABLE_DIR`.

Это позволяет запуск без установщика, но отличается от требования Tropa переносить собственные данные вместе с распакованной папкой. Предыдущее сравнение теперь уточнено фактическими путями, а не только названием ZIP.

### 3. MASQUE-регистрация делегирована usque

`src/main/main.ts:147` проверяет `config.json` и вызывает `spawnSync(usquePath, ['register', '-a', '-n', 'masque-plus'])`. Вызов находится до `setupInitialConfiguration`, где вызывается `copyRequiredFiles`; исключение поглощается пустым catch. По статическому порядку на первом запуске возможна попытка регистрации до подготовки бинарника. Код usque и реальное первое подключение в этом исследовании не запускались, поэтому это риск, а не воспроизведённый runtime-дефект.

Для Tropa сохранить последовательность: проверка ресурсов → регистрация нужного семейства → проверка ответа → атомарное сохранение → подключение. Не создавать MASQUE account на старте, если он ещё не требуется.

## Что не следует повторять

### Проверка готовности по тексту и HTTP 200

`wpManager.ts:69,369` распознаёт `serving proxy` по подстроке stdout. `sbManager.ts:157` делает обычный `fetch(testUrl)` и принимает `response.ok`. Это подтверждение доступности HTTP-ресурса, не самостоятельное доказательство прохождения конкретного приложения через WARP. Node stdout chunks не обязаны совпадать с границами лог-строк; версия бинарника может изменить текст.

В renderer есть отдельное чтение WARP trace (`useLanding.ts:77`), поэтому было бы неверно утверждать, что приложение нигде не проверяет WARP. Но условие `checkWarp !== 'off'` допускает и пустое значение при отсутствующем поле. Для Tropa допустимы только явно распознанные `warp=on|plus`; readiness и проверка полезного трафика — разные этапы.

### Непреднамеренно широкие обходные правила

При `config.socksIp === '0.0.0.0'` builder в `sbConfig.ts:159` создаёт `ip_cidr: ['0.0.0.0/0']` с `outbound: direct`. Это условная ветка, покрывающая все IPv4 destination до последующих правил, а не только локальный адрес listener. Фактический runtime-сценарий с таким сочетанием настроек не воспроизводился.

Там же имеются общие исключения портов и отдельный `udpBlock`, способный отвергать UDP. Для Tropa правила loop avoidance и LAN необходимо задавать узко и тестировать приоритет; игровой UDP нельзя незаметно отвергать или направлять DIRECT исключениями общего назначения.

### Исключения Defender/Bitdefender как восстановление

`wpManager.ts:125` предлагает диалог Add to Exceptions. После согласия создаются команды добавления сетевых EXE в исключения Defender/Bitdefender (`:160`), скрипт запускается с UAC. Этот путь вызывается при отсутствующем runtime EXE, если оригинальный asset ещё присутствует.

Это реальный механизм с запросом согласия, а не доказательство вредоносности приложения. Для Tropa он не нужен: отсутствие/карантин бинарника следует объяснить, проверить подпись/хэш и обработать ложное срабатывание без автоматического ослабления защиты.

### Состояние по имени процесса и задержка вместо подтверждения остановки

`sbManager.ts:477` использует tasklist/pgrep и проверку подстроки имени; `stopHelper` вызывает RPC и затем фиксированную задержку. `wpManager.ts:306` вызывает treeKill; продолжение завершения зависит от события exit.

Tropa уже использует владение собственным PID/runtime, execution guard и Windows Job Objects. Сохранить это; другой процесс с тем же именем не должен становиться «нашим», а sleep не является подтверждением завершения.

### Привилегированный helper требует отдельного анализа

Desktop-клиент подключается к `127.0.0.1:50051` через `grpc.credentials.createInsecure()` (`sbManager.ts:199`). В protobuf есть Start/Stop/Exit/StreamStatus. Серверная реализация helper находится в другом репозитории, и по клиенту нельзя установить все способы проверки вызывающей стороны.

Не объявлять здесь доказанную уязвимость. Если Tropa когда-нибудь разделит обычный UI и повышенный helper, нужен отдельный протокол с проверкой владельца и границ прав; простого переноса gRPC-клиента недостаточно.

### Загрузки и метрики требуют точных названий

В рассмотренных download-функциях `script/dlBins.ts:20,52` и `main.ts` не обнаружена явная проверка ожидаемого SHA/подписи перед распаковкой/использованием. Это вывод об этих функциях, а не об отсутствии всех механизмов защиты во всех внешних компонентах.

`useLanding.ts:122` называет ping временем выполнения HTTP trace. `NetStatsManager` измеряет выбранный системный интерфейс; его счётчики не равны трафику выбранного приложения или только WARP. Для Tropa нужны явные подписи «HTTP-проверка», «трафик ядра/туннеля», «игровой RTT» и отдельные источники.

## Какие изменения в плане Tropa следуют из анализа

1. В веху диагностики добавить конкретные причины UAC, offline и часов, сохраняя фактическую сетевую проверку и ограниченные повторы. Использовать типизированные события вместо сравнения текста логов.
2. В веху split tunneling добавить регрессионные сценарии противоположных политик include/exclude, одинаковых имён EXE в разных папках, широких bypass-правил и UDP block.
3. В MASQUE-регистрации явно проверить первое включение при ещё не подготовленных ресурсах. Сохранить ленивый запуск регистрации нужного семейства.
4. В DNS/lifecycle-проверки добавить bootstrap DoH, исключение outer endpoint из TUN и отдельную проверку полезного WARP-трафика после readiness.
5. Для минимального UI оставить статус/причину и отдельные подробности; статистику, если добавлять, брать из API mihomo. Не включать непрерывные speed tests.
6. В portable-проверке контролировать фактические пути, перенос data и отсутствие служебных файлов в чужих каталогах. Восстановление бинарников не должно добавлять antivirus exclusions.

Эти выводы уточняют существующий план; сами функции Tropa этим исследованием не изменены. Оснований заменять весь клиент или добавлять второе сетевое ядро не обнаружено. Результат не подтверждает превосходство производительности и не устанавливает совместимость с античитами.
