# Tropa: проверка основы и portable-запуска

> Статус: обновлённый план проверки, не отчёт о выполнении. После рассмотрения спецификации подготовить актуальный план получения исходников с конкретными командами. По умолчанию работа выполняется последовательно в текущем чате.

**Goal:** Получить первую сборку в проекте Tropa и проверить пригодность Clash Verge Rev, mihomo и WarpScout для portable-клиента Windows до изменения интерфейса.

**Architecture:** Сначала воспроизводим неизменённую upstream-сборку с одним ядром и отдельным сканером, затем отдельно проверяем portable-запуск. Если нужна адаптация запуска, она оформляется отдельным ограниченным экспериментом с сохранением исходного результата. Результаты проверки служат входом следующего плана разработки; собственная игровая функциональность в этот этап не входит.

**Tech Stack:** Windows 11 x64, PowerShell, Git, Clash Verge Rev v2.5.8 как исследованный исходный ориентир, upstream mihomo, WarpScout, штатные средства диагностики Windows. Версии Rust, Node и менеджера пакетов определяются закреплённым checkout.

**Spec:** `docs/superpowers/specs/2026-10-27-game-warp-design.md`

## Global Constraints

- Первая целевая платформа — Windows 11 x64; Windows 10 x64 получает статус поддержки только после отдельной проверки совместимости и политики upstream.
- Во время подключения работает одно сетевое ядро: mihomo; после отключения принадлежащий Tropa экземпляр завершается.
- WarpScout запускается по запросу; постоянное фоновое сканирование выключено.
- Выбранные процессы направляются через выбранный туннель; остальной трафик по умолчанию идёт напрямую.
- Маршрут не переключается автоматически во время матча.
- Ключи WARP, индивидуальные конфигурации и необработанные журналы соединений не публикуются в Git.
- Собственные сетевые драйверы и внедрение кода в процессы игр в первую версию не входят.
- Portable-поставка не требует установщика и постоянно установленной службы. Права администратора допустимы. Бренд, идентификаторы и обновления отделяются от upstream перед первым распространяемым архивом.
- Тесты не выдают ICMP или HTTP-задержку за измерение игрового RTT.
- Публикуемые исходники и бинарники должны выполнять лицензии включённых компонентов.

---

## Границы выполнения

Это план проверяемого первого этапа. Изменения продукта начинаются по отдельному плану после решения об оболочке. Основные задачи здесь ручные и измерительные, с явно заданными ожидаемыми результатами. При необходимости изменения portable-запуска сначала оформляется отдельный план по фактическим исходникам с проверкой его поведения; такие изменения не выполняются скрыто внутри измерений.

Длительные действия — сборка и игровые сессии — естественно длиннее 2–5 минут; короткие шаги выделены отдельно. Новые версии компонентов не подменяются автоматически во время сравнения.

### Task 3: Проверить WARP и раздельное туннелирование

**Files:** создать `docs/validation/connectivity.md`; приватные конфигурации хранить вне репозитория.

**Interfaces:** принимает рабочую сборку и команды Task 2; выдаёт матрицу `режим × проверка` с результатами PASS/FAIL/UNAVAILABLE и доказательствами без секретов.

- [ ] Сохранить локально исходные маршруты, DNS и наличие других VPN. На время контролируемого сравнения исключить одновременную работу конфликтующего VPN согласованным способом; не удалять чужие настройки.
- [ ] Проверить portable-контракт по разделу 13 спецификации: запуск без установленной службы, UAC и отказ, расположение данных, WebView2/драйверы, второй экземпляр, перенос папки и остаточные изменения после завершения. Записать в connectivity.md доказательства до/после и зависимости. ZIP от upstream без этой проверки не считать подтверждением portable.
- [ ] Измерить direct: доступность тестовой HTTPS-цели и игровой вход. Записать дату, провайдера, метод и результат. Не считать один неуспешный ICMP отказом сервиса.
- [ ] По командам Task 2 получить кандидаты WireGuard/WARP, MASQUE H3 и MASQUE H2, если они поддержаны фактической сборкой. Для каждого записать endpoint, фактический colo при доступности и результат обмена через туннель. Отсутствующий транспорт пометить как неподдержанный, блокируемый или неустановленный по полученным доказательствам.
- [ ] Создать локальный профиль mihomo с выбранным тестовым процессом через WARP и завершающим DIRECT-правилом. Синтаксис взять из документации зафиксированной версии; включить получение метаданных процесса предусмотренным способом.
- [ ] Выполнить одинаковый запрос из выбранного и невыбранного процессов. Сопоставить цепочку маршрута в API ядра и наблюдаемый внешний адрес, если цель позволяет. Убедиться, что выбранный процесс идёт через WARP, а второй — DIRECT. Проверить IPv4 и IPv6 при наличии; отсутствие IPv6 записать как границу проверки.
- [ ] Проверить DNS и обращения к локальной сети в direct и tunnel. Записать фактический способ резолвинга и случаи, когда DNS не позволяет соблюсти ожидаемое поведение. Не объявлять изоляцию DNS по одному правилу процесса.
- [ ] Проверить штатное отключение, завершение ядра, сон/возобновление и восстановление подключения. Выполнять аварийную проверку вне игры. После каждого случая проверить обычный HTTPS, DNS и маршруты.
- [ ] Записать в `connectivity.md` таблицу: сценарий, транспорт, метод, ожидаемый результат, фактический результат, PASS/FAIL/UNAVAILABLE, ограничение доказательства. Удалить из отчёта ключи и личные пути.

```powershell

```

Отдельно подтверждён portable-контракт: без постоянно установленной службы, с известными зависимостями и проверенным восстановлением. При невозможности — INVESTIGATE_SHELL.

### Task 6: Принять решение и подготовить следующий план

**Files:** создать `docs/decisions/0001-shell-selection.md`; обновить `docs/roadmap.md` при изменении направления.

**Interfaces:** принимает отчёты Tasks 2–5; выдаёт одно основное решение по разделу 15 спецификации: CONTINUE_FORK, INVESTIGATE_SHELL, INVESTIGATE_TRANSPORT, INSUFFICIENT_EVIDENCE или USE_UPSTREAM_ONLY, с фактами и последствиями.

- [ ] Сопоставить результаты с ограничениями спецификации. Для каждого требования указать отчёт и результат, не заменяя отсутствующую проверку предположением.
- [ ] Применить правило решения: CONTINUE_FORK при рабочей сборке, выполненном portable-контракте, процессной маршрутизации, восстановлении сети, полезном игровом сценарии и согласованном бюджете ресурсов; INVESTIGATE_SHELL при локализованной проблеме оболочки; INVESTIGATE_TRANSPORT при отказе нужного пути или функции ядра.
