# Tropa: регистрация WARP и последовательность подключения

> Исторический проект импорта. Пользователь изменил сценарий: ручной импорт и лицензии исключены. Актуальное решение — [автоматическая регистрация и сброс](2026-10-27-automatic-warp-design.md). Сведения о формате/хранении ниже остаются исследовательской основой, порядок пользовательских действий заменён новым проектом.

Дата: 27 октября 2026 года. Документ подготовлен для рассмотрения перед реализацией. Название, portable-режим, импорт регистрации в первом сетевом срезе и хранение без обязательного шифрования опираются на решения пользователя в чате. Автоматическая регистрация описана как следующий отдельный этап.

## 1. Что строим первым

Настройки → Профиль WARP → Импортировать файл → выбрать собственный `warpscout-account.json` → получить состояние «Регистрация импортирована». Повторный запуск сохраняет регистрацию. Пользователь может заменить или удалить принадлежащую Tropa копию. Исходный файл не изменяется.

Импорт подтверждает корректность структуры и локальное сохранение. Он не подтверждает, что Cloudflare принимает регистрацию, что endpoint доступен или что игра идёт через туннель. Главный переключатель остаётся недоступным до реализации и проверки координатора подключения.

Первый поддерживаемый транспорт — WireGuard в mihomo. Из файла WarpScout импортируется основная регистрация; вложенные `masque` и `outer` не копируются и не используются. На экране импорта это ограничение объясняется. MASQUE требует отдельного решения по совместимости регистрации с выбранным ядром; не подставляем в него ключи WireGuard.

## 2. Рассмотренные варианты

1. **Импорт собственной регистрации первым — рекомендуемый порядок.** Позволяет отдельно проверить данные, сохранение и транспорт, используя уже существующий экспорт WarpScout. Первый запуск временно требует внешнего получения регистрации.
2. **Автоматическая регистрация сразу.** Удобнее для пользователя, но одновременно добавляет внешний API, отказы сети, ограничения частоты, сохранение выданных реквизитов и восстановление после частичного сбоя. Это самостоятельный следующий план.
3. **Одна регистрация внутри общего архива.** Не подходит задаче независимых пользователей: копии приложения используют одну идентичность. Такой файл не включается в поставку.

## 3. Идентичность и хранение

Portable-поставка — ZIP с готовой папкой: Tropa.exe, DLL, отдельные сетевые компоненты и ресурсы по необходимости. Упаковывать всё в один exe не требуется. После распаковки пользователь запускает Tropa без установки дополнительных пакетов; состав runtime проверяется на чистой Windows перед поставкой.

- Регистрация принадлежит конкретному пользователю, получившему её у Cloudflare. Идентификатор выдаёт Cloudflare; случайный локальный ID приложения его не заменяет.
- Путь хранения: `app_home_dir()/secrets/warp-account.json`, то есть `data/secrets/warp-account.json` в Windows portable.
- Файл обычный, без DPAPI, дополнительного пароля и обязательного шифрования. Сохраняются ID, токен, приватный ключ, публичный ключ пира и адреса туннеля в собственном формате версии 1.
- Файл не содержит endpoint: смена точки подключения не требует замены регистрации.
- Копирование всей папки с этим файлом переносит ту же регистрацию. Для независимого устройства получают другую регистрацию. Копирование не создаёт новый ID автоматически.
- Нет привязки к аппаратному отпечатку. Нет общей регистрации в бинарнике, примерах, тестах или архиве поставки.
- Реальные данные исключаются из Git, журналов, ответов frontend, диагностики и обычных резервных копий. Это исключение из экспорта, а не обещание защиты от чтения локального файла.

## 4. Принимаемый импорт

Корневой JSON-объект WarpScout: обязательные непустые строки `id`, `token`, `private_key`, `peer_public_key`, `ipv4`; необязательная строка `ipv6`. Ключи декодируются из standard base64 в 32 байта, нулевые ключи отклоняются. IPv4 и IPv6 проверяются по семейству адреса. ID и токен сохраняются как выданные значения; не придумываем им формат UUID.

Максимальный размер входного файла — 256 KiB; чтение ограничивается до разбора JSON. Отсутствующие обязательные поля, неправильные типы, невалидные ключи/адреса и неподдерживаемая версия собственного файла дают ошибку. Ошибки не включают исходный JSON или значения полей. Вложенные регистрации и неизвестные поля не переносятся в нормализованную запись.

Валидация формата не является криптографической проверкой Cloudflare. На этом этапе нет запроса к Cloudflare, запуска WarpScout или mihomo, TUN, изменения маршрутов либо получения прав администратора.

## 5. Владельцы и интерфейсы

`src-tauri/src/config/warp_account.rs` владеет разбором, нормализацией, чтением, атомарной заменой и удалением. Секретная модель не имеет `Debug`; команды не возвращают её в webview. Для frontend предусмотрен статус `missing` либо `imported` с признаком наличия IPv6. Неисправное хранилище возвращает ошибку, а не выглядит как пустое.

`src-tauri/src/cmd/warp_account.rs` предоставляет `get_warp_account_status`, `import_warp_account(path)` и `remove_warp_account`. Операции сериализуются существующим `Config::lock_config_write`. Команда получает путь, а не ключи в аргументах. В tracing используется `skip_all`; сообщения об ошибке очищаются на границе разбора/ввода-вывода.

`src/services/tropa.ts` владеет вызовами команд и выбором файла. Страница использует `useQuery` и общий `mutate` с одной идентичностью ресурса; повторные действия блокируются до завершения. Состояние меняется после успешного сохранения, ошибки показываются в текущем экране без повторных уведомлений.

Сначала файл полностью проверяется, затем нормализованная запись сериализуется и заменяется существующим атомарным writer. Временный файл находится внутри `secrets`. Ошибка импорта сохраняет предыдущую регистрацию. Удаление касается только этой копии; отсутствие файла при повторном удалении считается успешным результатом. Повреждённый файл не сбрасывается автоматически; пользователь может явно удалить его или заменить новым импортом.

В первом этапе активного потребителя регистрации ещё нет. Перед интеграцией подключения координатор обязан запрещать её замену/удаление, пока она используется активной или восстанавливаемой сессией. Это проверяется до активации переключателя, а не заменяется проверкой «любое ядро запущено»: upstream уже может запускать ядро без игрового подключения.

## 6. Интерфейс

При отсутствии регистрации экран предлагает импорт и короткую инструкцию получения собственного файла через WarpScout. После импорта показывает «Регистрация импортирована», «WireGuard» и действия замены/удаления. ID, токен и ключи не отображаются. Перед заменой и удалением требуется явное действие пользователя; ошибка чтения не должна делать эти восстановительные действия недоступными.

Возле выбора поясняется: «Файл хранится локально без шифрования. Копирование папки переносит эту регистрацию». Форма не требует пароля и не превращает это пояснение в отдельное согласие. На главном экране после импорта написано «Регистрация добавлена; подключение ещё не настроено», а не «Подключено».

## 7. Проверки первого этапа

Реальные файловые проверки на синтетических реквизитах: успешный импорт и повторное чтение; отклонение неверного файла с сохранением прежнего; ограниченный размер входа; повреждённый сохранённый файл; отсутствие права записи; удаление только принадлежащей Tropa копии; отсутствие секретов в DTO и диагностических сообщениях.

Браузерные проверки: отсутствие регистрации, успешный импорт, отмена выбора, ошибка, повторное нажатие, замена, удаление, оба пути возврата через «Назад», тёмная/светлая темы. В browser preview используются явно синтетические данные, native picker проверяется отдельно в приложении. Никакой реальный ключ не попадает в фикстуры.

Текущий `core/backup.rs::create_backup` собирает конкретные конфиги и содержимое `profiles/`, а не всё дерево data: `secrets` остаётся вне этого набора. Текущий `export_diagnostic_info` копирует системную информацию в буфер обмена, не архивирует data. Изменять их без обнаруженного нарушения не требуется; перед подключением дополнительно проверяются сгенерированные runtime-конфиги, поскольку в них появятся ключи.

## 8. Следующие самостоятельные этапы

| Порядок | Результат | Условие перехода |
|---|---|---|
| 0, до первого нативного сетевого запуска | Изоляция upstream-обновлений и кэша установленных обновлений, закрепление бинарников | Tropa не устанавливает обновление Clash Verge Rev ни фоновым, ни ручным, ни стартовым путём |
| 1 | Импорт собственной регистрации и локальное хранение | Тесты выше проходят, старый файл переживает ошибку, UI не сообщает о подключении |
| 2 | Проверенный транспорт через одну явно выбранную точку | Есть передача данных, отдельно проверен игровой UDP; отказ WireGuard приводит к исследованию другого транспорта, а не имитации успеха |
| 3 | Координатор одной игры, права и реальный переключатель | Игра идёт через WARP, контрольный процесс напрямую; повторные операции сериализуются; отключение и выход восстанавливают подтверждённые изменения |
| 4 | Проверка восстановления и portable-испытания | Проверены сбой ядра/оболочки, UAC-отказ, перезапуск, сон, конфликты и существующая служба; неподтверждённое восстановление отображается явно |
| 5 | Автоматическая регистрация собственного устройства | Новая копия без реквизитов создаёт свою регистрацию; повторный запуск переиспользует её; API-ошибка не затирает старую; прямой запрос и альтернативные пути согласованы отдельно |
| 6 | Встроенный WarpScout и выбор проверенных точек | Кандидаты имеют результаты реальных проверок; во время матча нет самовольной смены маршрута |
| 7 | Portable ZIP для испытаний | Нет пользовательских реквизитов, проверены лицензии/состав, запуск на чистой Windows и отсутствие обязательной постоянной службы |

Автоматическая регистрация не должна вызывать `warpscout register` при каждом запуске: повторный вызов может менять ключи. Регистрация через стороннее реле не включается молча. Применимость API и совместимость транспорта проверяются на закреплённой версии перед реализацией этапа 5.

Подробный план первого этапа: [импорт регистрации](../plans/2026-10-27-warp-account-import.md). Каждый следующий сетевой этап получает свой конкретный план по фактическому результату предыдущего.
