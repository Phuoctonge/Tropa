# Tropa: автоматическая регистрация WARP

Согласовано в чате: первое подключение автоматически регистрирует устройство, следующие используют сохранённую запись; в настройках только «Сбросить регистрацию». Ручной импорт и лицензионные ключи исключены из пользовательского сценария. Этот документ заменяет соответствующие решения раннего проекта импорта.

Backend предоставляет ensure/reset. Ensure возвращает имеющуюся корректную запись без сети; если записи нет, создаёт X25519-пару локально и регистрирует публичный ключ прямым HTTPS-запросом Cloudflare. Reset создаёт новую регистрацию с новой парой, заменяя старую лишь после успешного включения WARP и атомарного сохранения. Повреждённая запись не считается отсутствующей; reset позволяет восстановиться явно. Свежие независимые папки получают разные регистрации; перенос папки с secrets переносит прежнюю идентичность. Аппаратной привязки нет.

Протокол проверен по WarpScout 9e2ce9570625757ba24b390ad680dccd5e7f2707/register.go: POST https://api.devices.cloudflare.com/v0a4005/reg с JSON {key: publicKey}, затем PATCH /reg/{id} с Bearer token и {warp_enabled:true}. Заголовки CF-Client-Version a-6.11-2223 и User-Agent okhttp/3.12.1. Токен/приватный ключ/ID не возвращаются в webview и не журналируются. Прямой транспорт без системного proxy, стороннего relay, redirect и автоматических повторов POST. Ограничение ответа 64 КиБ, таймаут запроса 15 секунд, подключение 5 секунд.

Локальное plaintext-хранилище версии 1 сохраняется. Промежуточная новая запись сохраняется в secrets/warp-pending.json до PATCH, поэтому сбой включения или финальной записи повторно использует уже созданную регистрацию. Старый основной файл при этом остаётся авторитетным. Если POST завершился на сервере, но ответ или предварительное сохранение потеряны, возможна неиспользуемая удалённая регистрация; автоматических повторов и обещания транзакционности удалённого API нет. После финального сохранения остаточный pending распознаётся по ID и очищается до следующего reset.

Все ensure/reset/status сериализованы config-write lock. Активного Tropa-туннеля ещё нет; при его добавлении reset обязан запрещаться при активной/восстанавливаемой сессии. Запущенное upstream-ядро не заменяет проверку этой сессии.

Явный reset может удалить повреждённую/нечитаемую промежуточную запись; если удаление не удалось, операция завершается до HTTP. При отсутствии основной записи ошибка чтения pending видна в статусе, чтобы сброс оставался доступен. Окончательный отказ активации 401/404/410 удаляет непригодный pending и возвращает ошибку без нового POST; следующая явная попытка может создать новое устройство. Временный сбой сохраняет pending для продолжения.

UI показывает «Устройство зарегистрировано» либо «Регистрация будет создана при первом подключении», сброс с подтверждением и понятную ошибку. Регистрация не означает работающий туннель. До реализации координатора главный переключатель остаётся выключенным и недоступным; ensure предназначен для его первого шага. Не добавляется отдельная обязательная кнопка регистрации. Реальное создание устройств при разработке не выполняется; HTTP проверяется локальным сервером, workflow — синтетическими регистрациями. Native smoke требует изоляции updater.

Новая прямая зависимость x25519-dalek 2.0.1 обоснована генерацией совместимой WireGuard-пары с экспортируемым приватным ключом; существующие TLS-интерфейсы не предоставляют нужный формат секретного ключа. Случайность — существующий getrandom. Обновление иных зависимостей не допускается.
